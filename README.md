# Run Analytics · 跑步数据分析仪表盘

把**小米运动健康 App 的官方隐私中心导出包**变成一个本地跑步数据分析看板：训练负荷模型、
跑姿体检、每日训练建议、训练日历与多维度对比。纯静态零构建，所有分析在浏览器本地完成——
**数据不出本机，不上传任何云端**。

## 它能给你什么

- **训练负荷模型（CTL / ATL / TSB）**：体能、疲劳、状态三条曲线，判断"现在该练还是该歇"，
  阈值采用跑圈通行口径（TrainingPeaks / Garmin 同款）。
- **每日建议卡**：按恢复窗口、近 7 天负荷、强度结构等优先级给出今天该歇还是该跑、
  跑多少、用什么配速——结论必须是可执行的动作，不是一句描述。
- **跑姿体检表**：步频 / 触地时间 / 垂直振幅 / 垂直步幅比对照通行参考区间，
  每项给"怎么改"的具体动作，并按最不达标的一项给优先改善建议。
- **训练日历**：26 周热力图，点任意一天看当日详情与同距离历史对照。
- **对比分析**：月度对比（控制距离变量）、跨年与赛季内对比、自然周节奏。

## 快速开始

1. 从小米运动健康 App 的**隐私中心 → 管理您的数据 → 申请导出**，等小米把通知发到你的邮箱。
2. 双击 **`从邮箱导入.cmd`**：它会取回最新一封的解压密码，自动用脚本自己的浏览器下载
   **最新一份**导出包到项目的 `inbox/` 并导入，然后弹窗告诉你。
   （**只有这条路**：2026-09-24 起导入窗口里不再有「拖 zip + 输密码」，
   手动导入只剩命令行的 `python tools/import_zip.py <zip 路径>`。）
3. 导入完成点「打开历史看板」，或直接双击 `index.html`。之后不导入也能随时看已有数据。

零构建、零第三方运行时依赖（Chart.js 已内置于 `vendor/`）。

## 数据与隐私

- 所有数据保存在本地 `data.js`（生成物，已被 `.gitignore` 排除），**健康数据不进仓库**。
- 导入器只读取导出包中的两个跑步相关 CSV 成员，其余成员（含个人信息）一律不打开。
- 密码只在内存中存在，不落盘。

也可以被 [apex-console 总控台](https://github.com/duofulang007/apex-console) 作为模块接入，
双启动方式并存（独立使用 / 总控台启动）。

## 提交口诀（双仓库协作）

- 改了**本仓库**的任何文件 → 在本仓库根目录 commit / push。健康数据（`data.js`）已被
  `.gitignore` 排除，不会误传。
- 改了总控台的**模块接入层**（`apex-console/backend/modules/Run Analytics/`）→ 那属于
  **总控台仓库**，去那边提交。
- 自检跟着仓库走：本仓库改完跑 `node tools/check.js --browser`；总控台改完跑它的
  `node smoke-test.js` 与 pytest。

## 数据来源与获取方式

1. 浏览器打开 `account.xiaomi.com`，登录小米账号。
2. 进入 **隐私中心 → 管理您的数据 → 小米运动健康 → 申请导出**。
3. 收到邮件后下载 zip，解压得到一批 CSV。

一次导出即包含全部历史，**不需要逐条导出，也不需要抓包**。

### 哪些环节能自动化

从「申请导出」到「看板更新」一共 10 步，全部由 `从邮箱导入.cmd`
（即 `tools/fetch_from_mail.py` + `tools/auto_download.py`）接管。
**唯一的例外是首次登录**：小米的下载链接认 `account.xiaomi.com` 的登录态，无 cookie 的
裸请求会被重定向到登录页（实测确认）。所以脚本用**它自己的 Edge**（独立 profile，
不是你日常那个）——平时**无头静默跑，不出现任何窗口**；只有登录态过期时才开一个全屏
窗口把你叫过去登录一次（账号密码或微信扫码都行），登录态归脚本所有 —— 之后全自动。

| 环节 | 状态 |
|---|---|
| 1 登录小米账号 | **双击 `登录小米账号.cmd`**（2026-09-25 新增）：自动开页 → 关 cookie 条 → 勾「已阅读并同意」→ 填账号密码（没配置就把表单留给浏览器自动填充）→ 点登录。**到此为止**。与下载器**共用同一个 profile** |
| 2 隐私中心 + 短信 + 申请导出 | **由人做**—— 自己进隐私中心、过短信、申请导出（登录控件到此为止，不代做敏感操作） |
| 3 等提取完成 | 手动等（**只有这几小时压不掉**：包和解压密码都只在邮件里） |
| 5 等邮件到达 / 6 取解压密码 | **已自动** |
| 7 打开下载页 / 点「文件 #1」 | **已自动**（脚本自己的浏览器点） |
| 8 传递密码 / 9 导入重建 data.js / 10 打开看板 | **已自动** |

```bash
python tools/fetch_from_mail.py --check     # 只连邮箱、列出候选邮件
python tools/fetch_from_mail.py --peek      # 打印最新邮件的结构（密钥打码），用来校准正则
python tools/fetch_from_mail.py --dry-run   # 只说会用哪个本地包、有几个密码可试
python tools/fetch_from_mail.py             # 取密码 → 自动下载 → 导入
python tools/fetch_from_mail.py --notify    # 同上，成功后弹窗告知「可以打开看板了」
python tools/test_fetch_from_mail.py        # 离线自测：解析、判定与取信策略，不连网
```

双击 `从邮箱导入.cmd`（不带参数）就是 `--notify` 那条路。实际体验：

1. 双击，它连上邮箱取回解压密码；
2. 它**静默**跑完下载：无头浏览器，**屏幕上不出现任何窗口**，也不抢你的前台
   （实测 4 秒跑完）—— 只有**登录态过期**那一次，它才会换成全屏 Edge 窗口并置前，
   让你登录（账号密码或微信扫码）；
3. 它自己点「文件 #1」，包直接落到项目的 `inbox/`（不经过系统下载目录）。
   不用等浏览器那套下载通知，拿到直链就直接取回来；
4. 导入完成弹一个小窗：「数据已更新，可以打开历史看板了」。

**从第二次导出开始，你只需要在小米 App 里申请一下，剩下的就是等弹窗。**

九个设计取舍：

- **走 IMAP，不走 `wx.mail.qq.com` 网页版。** 网页版需要人登录、会改版，还会把「抄密码」
  变成手艺活；`imap.qq.com:993` + 授权码只读正文，稳定得多。凭证走环境变量
  `QQ_MAIL_USER` / `QQ_MAIL_AUTH_CODE`，或 `local/mail_config.json`（`local/` 已被
  `.gitignore` 排除）。授权码在 QQ 邮箱「设置 → 账户 → IMAP/SMTP 服务」里开启后生成。
- **解压密码仍然不落盘。** 从邮件里解析出来后只在本进程内存里，经环境变量传给导入器，
  用完即弃 —— 和导入窗口完全一致。会变的密码不存，长期凭证才存。
- **两段式取信，不白拉流量。** 先用「只取 FROM/SUBJECT/DATE 头部」的轻请求挑候选，
  再只对候选拉整封；已处理过的 UID 在发请求之前就跳过。旧写法是一封不留地拉整封再本地
  过滤，邮件一多就是分钟级，附件也白拖。
- **只用 `BODY.PEEK[]`，连「已读」这种副作用都不留。** `RFC822` 等价于 `BODY[]`，
  会把邮件标记成已读 —— 那等于替用户改动了邮箱状态，这个工具只读。
- **自动下载用脚本自己的浏览器（独立 profile），不是你日常那个。** 登录态由
  `local/browser-profile/` 保管（`local/` 已 gitignore），Playwright 直接驱动本机**已装的
  Edge**，**不用再下载 150 MB 的浏览器**，也不会在出错时改弹 Chrome 或你的默认浏览器。
  ⚠️ 登录之后那个目录等于一个登录着的小米账号 —— 别提交、别打包分享；想作废就删掉重新扫。
- **默认静默：无头跑，不出现任何窗口，也不抢前台。** 有头启动实测会抢前台
  （启动前前台是别的程序，启动后变成 Edge）—— 所以设计约束就是全程后台静默、不抢前台，
  最彻底的做法是根本不开窗口。只有登录态过期那一次才开全屏窗口
  并置前（无头里没法扫码）。排查问题用 `--show` / `--windowed`。
- **包不等浏览器的下载事件。** 点「文件 #1」之后，脚本拦下那个 `.zip` 的签名直链、
  掐掉浏览器自己那一份，再用浏览器上下文的请求器（带着登录 cookie）取回来 ——
  实测服务端 2 秒就绪、静默全程 **4 秒**。**不要**改回「等 `download` 事件」那套：
  实测那次事件 92 秒都没发出来，老版本就卡在这儿，最后降级去开默认浏览器，
  屏幕上莫名其妙多一个窗口。
- **新旧只认「哪份更新」，不认场数多少。** 本地有多个包时按**文件名里的导出日期**
  （小米的包以 `20260923_` 开头）挑最新的那个，不看文件 mtime —— 重下一份旧包会让 mtime
  变新，按它挑就会挑错。写入前也只比「最新一场的日期」：比看板旧才拒绝（返回码 6），
  场数少只是打一行提醒（导出侧的坏时间戳会被年份规则滤掉，场数少不代表包旧）。
  判据只有一份：`import_zip.package_stamp`，窗口预选、邮件链路、命令行都调它。
- **多个密码靠试（按「新的先试」）。** 邮箱里可能积着好几封导出通知、每封一个密码，
  而本地那个包不一定就是最新那封邮件的包 —— 依次试，导入器返回 4（密码错）就换
  下一个；遇到 6（包比看板旧）这类确定性错误则立刻停。

### 用到的文件

| 文件 | 作用 |
|---|---|
| `*_MiFitness_hlth_center_sport_record.csv` | 每次运动的汇总。Value 是 JSON，含 62 个字段，其中跑姿三项为 `avg_touchdown_duration`（触地时间）、`avg_vertical_amplitude`（垂直振幅）、`avg_vertical_stride_ratio`（垂直步幅比） |
| `*_MiFitness_hlth_center_fitness_data.csv` | 逐分钟序列。`Key=steps` 给每分钟步数与距离（可换算步频与配速），`Key=heart_rate` 给每分钟心率 |
| `*_MiFitness_hlth_center_aggregated_fitness_data.csv` | 日维度汇总（睡眠、静息心率、最大摄氧量等） |

**官方导出不含 GPS 轨迹。** 需要地图时，在 App 里单条导出 TCX 补上。

## 已知的两个坑

1. **导出文件没有扩展名。** App 导出的 TCX / GPX / KML 全叫「小米运动健康」，必须靠内容嗅探
   （`<gpx` / `<kml` / `<TrainingCenterDatabase`）判断格式。
2. **时区不一致。** TCX / GPX 里的时间戳是**本地时间却标了 `Z`**；而 CSV 里的是**真实 UTC**。
   拍同一场跑步，两边相差 8 小时。对齐时必须换算，否则曲线整体错位。

## 使用

**唯一路径：双击 `从邮箱导入.cmd`**（或打开导入窗口点那个品牌色按钮）。密码从邮件里取，
只用于本次解析、不保存；窗口里实时打印进度，成功后点「打开历史看板」——
开的是零侵入的极简外壳（`shell/minimal.html`：不缩放、不装饰，看板直接铺满窗口，
浏览器地址栏与原生滚动条都保留），看板本体一个字节都没改；
想连看板内部的选中一起禁掉（"像 App"那一条）就双击 `打开看板.cmd`。

窗口只有四个东西：**从邮箱导入 / 打开历史看板 / 清理下载的包和记录 / 日志**。
2026-09-24 起去掉了「拖 zip 进窗口 + 输入解压密码」那一套 —— 实测只用得上邮箱这条路，
控件越少越不容易点错（样式对齐总控台 apex-console 的设计令牌）。

**不导入也能看**：只要 `data.js` 存在（导入过一次就会有），窗口打开时「打开历史看板」
就直接可用，按钮下会显示当前数据概况（场次 / 截至 / 生成时间）。时不时想看看而手头没有
新导出包的日子，开着窗口直接点它就行。

命令行等价写法：

```bash
python tools/import_zip.py                 # 自动在项目内 inbox / latest 里找最新的包
python tools/import_zip.py <zip 路径>       # 指定包
python tools/import_zip.py --list           # 只看会读哪两个成员、跳过哪些敏感成员，不需要密码
```

导入的语义是**全量重建**：导出包本身就是全部历史，所以每次都把 `data.js` 整体重写一遍，
不是追加。写之前会把当前版本备份成 `data.prev.js`；如果这次解析出的场次数**少于**上一版，
脚本会拒绝写入（返回码 6）——这条专治「某次导出漏了几天把历史吞掉」。

早期版本 `tools/extract.py` 需要手动解压、改里面的 `SRC` 常量，现在只作备用。

## 改完代码先跑自检

```bash
node tools/check.js              # 逻辑自检，无依赖，秒级
node tools/check.js --browser    # 额外用真实 Chrome 抽样 computed style
```

逻辑自检用 `vm` + DOM 桩把 `app.js` 真跑一遍，覆盖「所有页签 × 所有年份 ×
所有月份两两组合 × 每一个有记录的日子」，抓抛异常 / 拿不到元素 / 渲染出空内容。

但它**看不见 CSS**，所以 `--browser` 那一路很关键。实测踩过一次典型的坑：
`.cal button { background: … }` 的优先级 (0,1,1) 压过了 `.heat1` 的 (0,1,0)，
于是日历所有格子都退回同一个颜色 —— 桩里一切正常，真实浏览器里整片日历是空白的。
`--browser` 会抽样各档热力色的计算值并断言它们互不相同，这类问题才会暴露。

> `--browser` 需要 `playwright-core`：
> 先 `export NODE_PATH=<playwright-core 所在的 node_modules 目录>`，否则脚本会打印 skipped 而安静地跳过。
> 另外 `require("playwright-core")` 返回整个模块，浏览器类型在 `.chromium` 上，
> 且必须保留 `this`（`chromium.launch(...)`），解构出来单独调会报 `_playwright` undefined。

**3. 打开看板：直接双击 `index.html` 就行，不需要服务器。**

所有资源（`data.js`、`vendor/chart.umd.min.js`）都是相对路径的本地文件，`file://` 协议下
页签切换、hash 路由、图表绘制全部正常（已实测 0 报错）。这样打开永远不会因为
端口被占、服务进程退出而打不开。

只有当你想在别的设备上看，或者需要 `http://` 地址时，才用可选的服务方式：

```bash
python -m http.server 8899 --bind 127.0.0.1 --directory .
# 然后打开 http://127.0.0.1:8899
```

注意 `--bind 127.0.0.1` 只监听本机，**别人的电脑打不开这个地址**；而且这个服务是当前终端
的子进程，终端一关就失效。要分享给别人得另想办法（见下）。

## 分享给别人

看板是纯静态的，天然可以分享，但要先想清楚**这是你的个人健康数据**：

| 方式 | 做法 | 代价 |
|---|---|---|
| 直接发文件 | 把整个目录打包发给对方，对方双击 `index.html` | 数据落到对方手里，且之后更新要重发 |
| 局域网 | 服务改成 `--bind 0.0.0.0`，对方访问 `http://你的内网IP:8899` | 同一 WiFi 下可见，需要放行防火墙 |
| 公网链接 | 部署成静态站点（如 Cloudflare Pages / Vercel / 对象存储） | 需要把 `data.js` 上传到云端，与你「数据不上云」的前提冲突 |

默认建议第一种：可控、可撤回。如果只是想给对方看**某一张图**，直接截图更快。

## 页面说明

- **总览**：顶部一条**今日建议**（一句话结论 + 可点进日视图），下面是总体 KPI、距离与配速、
  月度跑量、心率区间分布，以及**训练负荷与状态**（CTL / ATL / TSB 三线）。
- **日视图**：把数据落到「天」的粒度上。
  - **今日建议大卡**：固定四段式——状态标签 → 一句结论 → 3 个关键数字 → 一句原因，
    整屏读完就知道今天该歇还是该跑。卡片下方是**依据列表**（一行一条：数据新鲜度、恢复、
    训练负荷、强度结构、最近 7 天、轻松跑配速），每行右侧带判定词，扫一眼就能核对。
    轻松跑的参考配速来自最近 30 天心率 130–155 场次的加权平均，也就是你自己的 Zone2 落点。
  - **训练日历**：最近 26 周的方块热力图，颜色越深里程越大，浅灰是休息日，黑框是今天。
    点任意一天看那天的详情。每列是一周，自上而下为周一到周日。
  - **单日详情**：那天的 KPI，加一份结构化清单：强度结构、恢复窗口（含训练负荷与结束时刻）、
    与之前 30 天同距离场次的心率/配速/触地对比。休息日给的是「前后各跑了多少」，而不是空着。
- **跑姿分析**：**先看一张「跑姿体检表」**——四项核心指标（步频、触地时间、垂直振幅、
  垂直步幅比）各自给出最近 20 场的均值、跑圈通行参考区间、判定档位，以及**具体怎么改**
  （节拍器起步值、跳绳/踝跳组数、核心训练动作）。表格下面是趋势图与散点相关性，
  最后只留两张表给不出的解读：两个相关系数 + 一句「优先改哪一项」。同一页所有数字都用
  同一个窗口（最近 20 场），不会出现两套打架的数值。
- **单次复盘**：选一场跑步，看逐分钟配速 / 心率 / 步频三线叠加、配速分布直方图、前后半程漂移，
  以及这一场的结构化清单（强度结构、恢复窗口、同距离对照、触地对照）。
- **对比分析**：拆成**三个子页签**（页面顶部切换，每个子页一屏读完、不出现页面滚动条）：
  - **月度对比**：**基准月与本期两个下拉可任选**（默认基准月跟随本期的上一月，手动改过就不再跟随）。
    一行结论卡 + 三张图（配速—心率散点、同距离档位心率、关键指标变化）。
  - **跨年与赛季**：2025 vs 2026 关键指标、2026 赛季内同距离对比、同距离档位对比、周训练量（2×2），
    结论卡压缩成一行短句。
  - **明细表**：月度与跨年两张逐指标表并排完整展示，图表子页里的结论以它们为依据。
  - 曾经同屏铺开全部内容（早期截图反馈「看不清」），改版要点：子页内图高 160–200px、
    结论只留短句、藏在 `display:none` 里的图切回来时必须逐个 `resize()`（Chart.js 经典坑）。
- **全部记录**：可排序、可筛选的原始数据表。

## 三个统计口径（改图之前先读）

跑量一变，直接比均值就会得出反向结论，所以本项目用不同口径分别回答不同问题：

| 口径 | 回答什么 | 注意 |
|---|---|---|
| 今日建议 | 今天该歇还是该跑 | 恢复窗口（`recover` 小时数 − 已过小时）优先；再看最近 7 天有没有连续跑满 6 天、跑量是不是一周内涨超 10%、无氧阈以下的时间占比够不够 |
| CTL / ATL / TSB | 体能是在涨还是在掉、现在累不累 | 负荷-恢复模型的通行口径（TrainingPeaks / Garmin 同款）：**每日负荷 = 当天所有场次 `train_load` 之和，休息日按 0 计入**。CTL=42 天指数加权（体能），ATL=7 天（疲劳），TSB=CTL−ATL（状态）。分区：<−30 负荷偏重 / −30~−10 生产性疲劳 / −10~+5 平稳 / +5~+25 新鲜 / >+25 偏休息。本数据近 70 天 TSB 落在 −33.7 ~ −0.3，长期处在生产性疲劳区，量级与通行阈值吻合，可直接用。**只跟自己的历史纵向比，跨设备没有可比性** |
| 最近 7 天 | 当下的节奏对不对 | 滚动 7 天窗口，看场次、里程、负荷与强度结构。与「自然周」口径不同：这里永远是「距今 7 天」 |
| 自然周（周一起） | 这一周比上一周怎么样 | 周与周之间保持在 ±10% 以内算可持续；涨超 10% 是一周内的受伤诱因 |
| 基准月 vs 本期 | 最近这个月有没有变好 | 默认基准月是上一月。2026-09 单次均 7.36 km 对 08 的 5.73 km（+28.5%），均值仍不可直接比，要看「同距离档位」与「同配速」两张图 |
| 2025 vs 2026 全年均值 | 两年整体差异 | 2025 均 3.5 km、2026 均 5.4 km，配速与步幅的差异主要来自里程，**不是退步**。卡片副标题已标注 |
| 2026 赛季内、锁定 5–7 km | 身体状态本身有没有变好 | 7 月及以前 14 场 vs 8 月及以后 16 场，配速只差 1.6%，心率降 3.5% |

四条必须遵守的呈现规则：

1. **「哪个方向算变好」逐指标判断**。距离被锁死后，配速变化等于强度变化而不是成绩；
   步幅收窄配步频上升本来就是「小步快跑」的正确方向。这两项不放进「正向 = 改善」的图里，
   只写在结论文字里作对照，否则会把慢跑和正确的跑姿变化都标成红色退步。
2. **不为了图表好看删慢速场次**。494 s/km 这类是热身或长距离慢跑，是真实数据，
   用平滑（单场图）和分层（对比图）处理，不删点。
3. **样本门槛**。任何两组的比较，每组至少 3 场才算变化率、才做档位对比。
   否则 1 场的月份会算出「最大摄氧量 +101.5%」这类荒唐数字。不达标时只展示原始均值，
   变化列留「—」，并明确写出被排除的档位与原因。
4. **强度分档要把「有氧」算进低强度**。判定「有氧底座够不够」用的是
   热身 + 燃脂 + 有氧（三者都在无氧阈以下）。只算热身 + 燃脂会把占大头的有氧跑误判成高强度，
   结论会完全反掉——这一条踩过。

## 建议与解读的呈现格式（改文案之前先读）

结论多、数字多，最容易变成一堵墙。所以统一成两种结构，不再写大段散文：

- **建议卡**（日视图顶部）：`状态标签 → 一句结论 → 最多 3 个关键数字 → 一句原因`。
  四段固定，整屏内读完。结论必须是一个动作（"今天降一档：跑短、跑慢"），不是一句描述
  （"你的负荷偏高"）。
- **依据 / 解读列表**（建议卡下方、单日详情、跑姿页底部）：一行一条，
  `标签 | 当前值 | 补充说明 | 判定词`。判定词用颜色分档（good / warn / bad），
  避免用户自己去心算"这个数字算好还是不好"。

两条边界：

1. **同一屏内不能出现两套口径的数字**。跑姿页的体检表和底部解读必须用同一个窗口
   （最近 20 场），否则会出现「表格说 165、结论说 160」这种自相矛盾（踩过）。
2. **只有真的算「风险」才标告警色**。跑量比前 7 天掉 37% 是主动减量，标成橙色告警会误导；
   只有一周内涨超 10% 才标 warn。

## 设计原则

- 纯静态，零构建，零后端。所有数据在本地文件中。
- **所有对比最终都要落到一句能执行的建议上**，而不是只丢一堆图。每个页签看完都应该知道
  下一步做什么：总量页给今日建议、跑姿页给「优先改哪一项 + 怎么改」、单次复盘给这场的
  强度与恢复窗口、对比页给「变好了没有」的结论。
- **一屏之内先给结论，再给证据，最后才是深度**。跑姿页的顺序就是范例：体检表在最上，
  趋势图在中间，相关性解读在最下。任何页面都不把长分析放在开头。
- 时间轴与统计口径统一写在 `tools/import_zip.py`，页面只负责呈现。
- 不在前端做插值填充：数据缺失就留空，宁可断线也不编造。
- 建议里说的「今天」用的是真实系统日期，数据截至最后一次导入。两者差 3 天以上，
  建议卡会自己提醒你数据过期了。
